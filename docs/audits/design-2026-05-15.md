### 4.2 New gaps surfaced

#### 4.2.1 Combat tracker — secondary row states missing (web)

`SURFACES.md §8` requires three visual row states: active turn
(brass rail), boss-NPC name in `--state-crimson-bright`, low-HP
(`hp_current / hp_max < 0.4`) HP value tints crimson-bright.

**Closed (2026-05-15) by T-AUDIT-2026-05-15-COMBAT-ROW-STATES.**

- Web `apps/web/app/components/CombatTracker.vue` — new pure helpers
  `isBossNpc(combatant)` and `isLowHp(combatant)`; template binds
  `combat-tracker__name--boss` and `combat-tracker__hp--low`
  modifiers; SCSS applies `--state-crimson-bright`.
- Mobile
  `apps/mobile/lib/features/combat/presentation/pages/combat_tracker_page.dart` —
  same helpers; `_CombatantRow` overrides the active / inactive name
  color when boss; `_StatLabel.lowHp` flag swaps the value
  TextSpan colour + weight on the HP stat.
- **Discriminator decision** — "Boss NPC" is signalled by a
  case-insensitive free-form status flag literal `boss` applied by
  the GM via the existing add-flag input. No spec change, no new
  canonical flag. The handoff does not define the discriminator,
  so the cheapest faithful interpretation was picked.
- Low-HP test boundary — strict `<` (`hpCurrent / hpMax < 0.4`),
  matches handoff "below 40 %" wording. Negative `hpCurrent` (damage
  overflow, schema-permitted) triggers via the same ratio. Guarded
  against `hpMax <= 0`.
- Tests — 10 new helper assertions (5 web, 5 mobile per facet);
  full web Vitest pass + full mobile `flutter test` pass.

#### 4.2.2 Dice roller — pushed-fail branch missing (web + mobile)

`SURFACES.md §9` edge case: "Push can fail (no new 6s). Production
renders the failure state with a darker divider and a 'no new
successes' line; mockup shows success (+2 successes)."

**Closed (2026-05-15) by T-AUDIT-2026-05-15-DICE-PUSH-FAIL.**

- Web `apps/web/app/components/sheet/SheetDiceRoller.vue` — new
  session-scoped ref `pushDelta: number | null` captures `preHits`
  before the `pushRoll` call and stores
  `roll.hits - preHits` after. Template adds two mutually-exclusive
  outcome lines (`dice-roller__push-outcome--fail` and `--success`)
  rendered only when `pushDelta !== null`. SCSS sets the spec-faithful
  darker top-border (`--brand-brass-shadow`) + italic body on fail;
  `--state-mystic-teal` accent on success. i18n: new
  `pushFailLine` / `pushSuccessLine` keys in EN + RU full, UK + EL
  stubs.
- Mobile
  `apps/mobile/lib/features/rolls/presentation/blocs/dice_roller/dice_roller_state.dart` —
  new optional `int? pushDelta` field with `clearPushDelta` sentinel
  in `copyWith`. Cubit captures `preHits` in `push()` and stores
  `pushed.hits - preHits` on success; `roll()` resets the delta to
  null. `_LastRollCard` accepts `pushDelta`; new `_PushOutcomeLine`
  widget renders the spec-faithful divider variant + italic on fail
  (`tertiary`/`outline` palette stand-in for the as-yet-untokenised
  `--brand-brass-shadow` in the mobile theme) and a tertiary accent
  on success. Mobile strings remain English-only (the whole dice
  sheet is awaiting an i18n pass — separate gap).
- Session-scoping rationale: the outcome line is _ritual feedback_,
  not a persistent label. A reloaded already-pushed roll keeps its
  pushed badge but does NOT replay the outcome line; the
  `pushDelta` is only meaningful immediately after the push action.
- Tests — 4 web Vitest helper assertions (new
  `SheetDiceRoller.spec.ts`) + 2 new mobile cubit blocTests
  (`pushDelta is 0 when push adds no new 6s`, `fresh roll resets
pushDelta to null`) + 1 updated assertion (the existing happy-path
  push test now also asserts `pushDelta: 1`). Full web vitest
  23 files / 505 tests pass + web typecheck pass + full mobile
  `flutter test` 250/250 pass + `flutter analyze lib test/features/rolls`
  0 issues.

#### 4.2.3 Share viewer — view-only triad partial (web)

**Closed (2026-05-15) by T-AUDIT-2026-05-15-SHARE-VIEWER-VIEWONLY —
doc clarification, no code change.**

Original finding stated `PATTERNS.md §12` required all three signals
on the share viewer; on re-read, that was a misclassification. The
spec's example list already names the share viewer under signal 1
alone (`"Share viewer entire sheet: no edit affordances at all"`),
and `SURFACES.md §10` explicitly describes the share viewer's
parchment chrome + top banner + star watermark + footer CTA as the
read-only affordance.

`PATTERNS.md §12` split into:

- **§12a Partial view-only — the triad.** Applies when a writable
  surface contains a subset of read-only data (player session DP,
  encounter cards, roster on a GM surface). All three signals
  together; never partial within the triad.
- **§12b Fully read-only — chrome differentiation.** Applies when
  the entire surface is read-only (share viewer, future archived
  snapshots). Signal 1 is mandatory; signal 2 + signal 3 are scoped
  out — chrome (parchment surface, top banner, star watermark,
  footer CTA) carries the message instead.

`AppShareViewer.vue:164–170` is spec-compliant under §12b. No code
change required.
